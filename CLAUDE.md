# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project overview

This is a MicroPython application for the [Pimoroni Presto](https://shop.pimoroni.com/products/presto) device (a Raspberry Pi RP2350-based touchscreen display) implementing a tiled Home Assistant dashboard, visually modeled on [compresto](https://git.hack-hro.de/kmohrf/compresto), built as an app on top of [TmOS](https://github.com/themissingcow/pimoroni-presto-tmos) (a vendored, MIT-licensed page-based OS/app framework — see `VENDORING.md`).

Code in this repo runs on-device under MicroPython, not CPython — even though `pyproject.toml` declares `requires-python = ">=3.13"`, that constraint only governs the host-side tooling environment (uv-managed venv used to run `mpremote`, `pytest`, etc.), not the code that gets deployed to the Presto itself. Do not assume standard CPython stdlib/library availability when writing device code; MicroPython's stdlib is a subset, and Presto-specific modules (`presto`, `picographics`, `picovector`, `touch`) only resolve on-device or under the test stubs in `tests/conftest.py`.

The device talks to Home Assistant **only over MQTT** (to an existing EMQX broker), never directly to HA's REST/WebSocket API — Node-RED (already running inside HA) bridges HA entities to/from a fixed MQTT topic contract defined in `dashboard/topics.py`. The firmware has no HA auth token and doesn't know HA entity IDs, only MQTT topic slugs.

## Tooling and commands

- Host dependencies (`mpremote`, `pytest`) are managed with `uv`:
  - `uv sync` — install/update the host-side dev environment
  - `uv run pytest` — run the host-side test suite (see "Testing" below)
- `mpremote` is the only supported way to talk to the physical device over USB/serial:
  - `mpremote connect list` — list connected serial devices
  - `mpremote cp <file> :<file>` / `mpremote cp -r <dir> :` — copy file(s) to the device
  - `mpremote run <file>.py` — execute a script on-device without persisting it to flash (fast iteration; does not overwrite `main.py`)
  - `mpremote reset` — soft-reset the device (re-runs whatever `main.py` is currently on flash)
  - `mpremote exec "..."` — run a one-off expression on-device
  - When multiple devices might be connected, target explicitly: `mpremote connect <PORT> ...`
  - **The watchdog fights `mpremote run`.** When the flashed `main.py` has `config.WATCHDOG_ENABLED = True`, it arms `machine.WDT` (~8s) — and `mpremote`'s soft reset does **not** clear the watchdog hardware. So any `mpremote run <script>` after a `main.py` boot inherits an unfed ~8s watchdog that fires mid-script, and the symptom is a host-side `serial ... ClearCommError (PermissionError(13))` with **no device traceback** (a hardware reset produces none) — which reads as a USB fault, not a watchdog. Confirmed on hardware. To bench-test: set `WATCHDOG_ENABLED = False`, `mpremote cp config.py :`, `mpremote reset`, then run scripts; restore `True` after. (`scripts/device_error_smoke_test.py` also re-arms + feeds a WDT defensively so it can run either way.)
- **`rshell` is deliberately not a dependency.** It pulls in an abandoned `pyreadline` 2.1 on Windows that hard-crashes on import under Python 3.13 (`collections.Callable` was removed), which in turn breaks `pytest` itself (its readline workaround only catches `ImportError`, not this `AttributeError`). Don't re-add it without fixing that first.
- **The device already has its own `secrets.py`** (WiFi credentials from prior experimentation) that is intentionally *not* mirrored in this repo (gitignored, and no local copy exists — see `secrets.example.py` for the expected shape). Do not `mpremote cp` a placeholder over the device's real `secrets.py`; MQTT credentials need adding to the existing on-device file directly, not generated fresh.

## Testing

- `uv run pytest` runs the full host-side suite (`tests/`) under desktop CPython — no device needed. **Always run it via `uv run pytest`, not bare `pytest`**, and note `testpaths = ["tests"]` in `pyproject.toml` deliberately scopes discovery — without it, path-less invocations walk the whole rootdir including `.venv/` and hang.
- `tests/conftest.py` stubs `presto`/`picographics`/`picovector`/`touch`/`ntptime`/`machine` into `sys.modules` (adapted from TmOS's own `tests/conftest.py`) so `tmos.py`/`tmos_ui.py` and everything in `dashboard/` can be imported and exercised on desktop Python. Use the `mock_presto_module`/`mock_touch_factory`/`mock_machine_module` fixtures it provides rather than re-stubbing hardware yourself. The `machine` stub's `reset_cause()` defaults to a clean power-on; `mock_machine_module` resets it and lets a test set `WDT_RESET`/`HARD_RESET` to exercise `dashboard/diagnostics.py`'s boot-reason reporting.
- Pure-logic modules (`dashboard/grid.py`, `palette.py`, `state_store.py`, `topics.py`) are fully unit-testable this way. Anything doing real socket I/O (MQTT) or real PicoGraphics rendering is not — those need on-device verification via `mpremote run`.
- **Passing host tests are not evidence the code runs on MicroPython** — they only prove the logic is correct against CPython + stubs. Before trusting a new module, `mpremote cp` it to the device and confirm it actually imports/executes there (see `scripts/device_smoke_test.py` for the pattern: import the module, print/exercise something from it, catch import errors early). This project has already caught real MicroPython-vs-CPython/TmOS-API gaps (wrong `full_res` default producing a 240x240 not 480x480 display, `Theme`'s automatic dpi-scaling silently doubling naively-set pixel values; RP2350 `machine.reset_cause()` being effectively binary — `WDT_RESET` for *any* software reboot including `machine.reset()`, `PWRON_RESET` for a cold boot *or* the reset button — which killed a reset-cause-based hang detector before `dashboard/diagnostics.py` switched to an uptime breadcrumb) that no amount of host-side testing alone would have surfaced.
- **MicroPython's compiler is pathologically slow importing modules with many small distinct literal constants** — confirmed on real hardware: `dashboard/weather_icons.py`'s first version (a plain Python list of ~800 `(x, y)` float tuples across 15 icons) took **32 seconds** to import, vs 14ms for an equivalent amount of data packed into a single `bytes` literal and decoded at runtime via `array.array` (see that module's docstring, and `scripts/flatten_weather_icons.py`'s `pack_icon()`). File size wasn't the driver — it's specifically the *count* of distinct small literals (likely O(n²) constant-pool handling in MicroPython's compiler). Any future data table of more than a few dozen numeric literals should use the packed-bytes-plus-`array`/`struct`-decode pattern from the start, not a plain nested-literal structure — host-side `pytest` cannot catch this, since CPython's compiler doesn't have the same behavior.
- `scripts/config_topic_smoke_test.py` isolates "does the device receive and correctly parse this device's real retained config message" from the rest of the app, the same way `mqtt_smoke_test.py` does for entity state — useful before trusting a Node-RED-authored `screens`/`tiles` payload to swap the live dashboard. The retained-config → multi-screen page-swap path (`DashboardApp._on_config_update`) has been confirmed working end-to-end on real hardware: real broker, real Node-RED-published payload, correct tiles rendered after the swap.
- `scripts/device_error_smoke_test.py` covers the idle-hang / device-error work on real hardware. **Confirmed on hardware so far**: `dashboard/` all imports; `_BoundedMQTTClient` connects with `SOCKET_TIMEOUT_S=4`; and a bounded-timeout socket read that expires **raises `OSError(110)` (ETIMEDOUT)** — so `OSError` is the real disconnect path and the `TypeError`/`IndexError` members of `DISCONNECT_ERRORS` are just defensive. Also confirmed: RP2350 `machine.reset_cause()` returns `3` (`WDT_RESET`) even for a plain `mpremote run` with no WDT armed — i.e. it's useless as a hang signal (hence the uptime-breadcrumb approach in `diagnostics.py`). **Still unverified**: the 150s keepalive hold (broker-side EMQX session-stability watch is the better test — see below), the WDT surviving an app switch, and a real WDT-fired reboot landing a `boot` error. The USB serial connection dropped mid-run once (`ClearCommError` / `PermissionError(13)`) after `connected = True` — likely a Windows CDC glitch on RP2350 native USB; re-run to classify.

## Architecture

- `tmos.py`, `tmos_ui.py`, `tmos_apps.py`, `tmos_themes.py` — vendored TmOS, unmodified. Do not hand-edit; re-vendor per `VENDORING.md` instead so diffs stay reviewable.
- `umqtt/simple.py` — vendored `umqtt.simple` (deliberately not `umqtt.robust` — its blocking `reconnect()` retry loop would stall TmOS's single-threaded cooperative asyncio run loop).
- `dashboard/` — this project's own app code, layered on top of TmOS:
  - `grid.py` — tile-grid math. **16-column base grid**, not compresto's original 4 — a `STANDARD_SPAN`-cell (4) tile reproduces compresto's original 114px visual tile size, but the finer base grid lets the systray occupy a properly slim, grid-aligned row instead of being forced to be a full tile tall. See the "Grid granularity" section of the project plan for the reasoning.
  - `palette.py` — compresto's exact color constants (ported verbatim) plus `PenCache` (lazy `display.create_pen()` memoization) and `color_for_thresholds()`.
  - `theme.py` — `CompressoTheme(DefaultTheme)`, giving TmOS's own native chrome (systray) a look consistent with the tile grid. Overrides `setup()` to pin `padding`/`systray_height` to explicit final pixel values *after* calling `super().setup()`, rather than setting raw class attributes — those two properties are in `Theme._dpi_scaled_sizes` and get silently multiplied by `dpi_scale_factor` (2, given this app's forced `full_res=True`) otherwise.
  - `state_store.py` — keyed pub/sub (`DashboardState`), adapted from compresto's `on_update`/`_dispatch_event` pattern. Keys are `"{domain}/{slug}"`, matching the MQTT topic contract's addressing.
  - `topics.py` — the MQTT topic/payload contract. Single source of truth for topic strings and payload shapes; `mqtt_client.py` and tile code both import from here rather than hand-building either. Includes `device_config_topic`/`parse_config_payload` for the retained per-device screens/tiles config topic (see below), and `device_error_topic`/`format_device_error_payload`/`parse_device_error_payload` for the retained diagnostics topic (see `diagnostics.py`).
  - `icons.py` — flattened vector icon path data (currently just the mdiHomeAssistant glyph). `picovector.Polygon.path()` on-device only accepts straight-line points, not SVG path syntax, so curved icons are pre-flattened host-side by `scripts/flatten_icon.py` and checked in as point lists here.
  - `weather_icons.py` — flattened vector path data for all 15 Home Assistant `weather.*` condition glyphs (`mdi:weather-*`, Apache-2.0), generated by `scripts/flatten_weather_icons.py`. Unlike `icons.py`'s plain list of `(x, y)` tuples, each icon is packed as `(lengths, data)` — a small tuple of subpath point-counts plus one `bytes` blob of fixed-point coordinates — because the plain-tuple format took 32 seconds to import on real hardware once scaled to 15 icons (see the testing section's MicroPython-compiler note above). `weather_icon.py` is the renderer: decodes the packed bytes via `array.array` and scales/translates them the same way `splash.py`'s `_draw_icon` does for the home-assistant glyph, at whatever pixel size `WeatherTile` asks for. See `VENDORING.md` for this baked-icon-set's attribution entry.
  - `splash.py` — the boot splash screen (icon + label), drawn directly to `os.display` by `main.py` right after `OS()` construction and before `os.boot()`'s blocking wifi/NTP connect, so something shows immediately instead of a blank screen. Needs no explicit teardown — `DashboardPage`'s first tick fully repaints over it.
  - `modal.py`, `tiles.py`, `page.py`, `app.py`, `mqtt_client.py` — tile/page/app implementation. `DashboardApp` (`app.py`) can expose more than one `DashboardPage` at once (switched via the systray's page tabs); its screens/tiles come from a retained MQTT message on `topics.device_config_topic(DEVICE_ID)`, applied at runtime via `DashboardApp._on_config_update`, not solely from `config.py`.
  - `mqtt_client.py` idle-hang fixes (see the "idle hang" investigation / project plan): `_BoundedMQTTClient` subclasses vendored `umqtt.simple.MQTTClient` and overrides `wait_msg()` — the vendored body reproduced verbatim from the pinned revision with the single mid-method `self.sock.setblocking(True)` (== `settimeout(None)`, block forever) changed to `self.sock.settimeout(SOCKET_TIMEOUT_S)`, so a stalled/half-open socket read raises instead of freezing the single cooperative run loop until a hard reset. **Re-check that copied body against upstream when re-vendoring umqtt.** `DashboardMQTT.tick()` also sends a `PINGREQ` every ~`keepalive/2` (`umqtt.simple` never pings itself and this app publishes nothing while idle, so without it the broker drops the session every ~90s and the device reconnect-churns), and catches `(OSError, TypeError, IndexError, AssertionError)` from `check_msg()`/`ping()` (a broken read surfaces as any of them on different ports) → `_handle_disconnect()`.
  - `diagnostics.py` — `BOOT_ID` (per-boot random hex), `reset_reason()` (guarded `machine.reset_cause()` wrapper), and `DiagnosticsReporter` which bridges `os.add_message_handler` (severity ≥ `MSG_WARNING`, rate-limited except `MSG_FATAL`) to `DashboardMQTT.report_error()` → the retained `device_error_topic`. **Hang detection is uptime-based, not reset-cause-based**: on the RP2350 `machine.reset_cause()` only distinguishes "watchdog" (which covers *every* software reboot — `machine.reset()`, `mpremote`'s soft reset, and a real WDT timeout alike) from "power" (cold boot *or* the physical reset button), confirmed on hardware — so it's payload context only. Instead: `init_boot_state()` (called from `main.py` before `DashboardApp.setup()`) reads a one-line breadcrumb file left by the previous boot, then resets it; `mark_long_run_if_due()` (an `os` task) flips the breadcrumb to `{"long_run": true, "uptime_s": N}` once the session passes `LONG_RUN_THRESHOLD_MS` (10min), refreshing hourly; `report_boot_reason()` (from `DashboardApp.setup()`) sees a `long_run` breadcrumb on the next boot and reports a `fatal`/`boot` error — a long previous session that ended in a reboot is a hang (a reflash or settings-reboot cycle is always shorter). `DashboardMQTT.report_error()` queues (bounded, drops oldest) while disconnected and flushes after subscribe in `_connect()`; a `_reporting` re-entrancy flag stops a disconnect path (or `wait_msg`'s mid-packet `self.cb`) from looping back into the socket.
  - `watchdog.py` — `WatchdogFeeder`: arms `machine.WDT` on its **first** `tick()` (not at construction — `os.boot()`'s blocking wifi/NTP can exceed the RP2350's ~8.3s max period), fed at 2Hz thereafter. Registered in `main.py` via `os.add_task()`, **not** as a `DashboardApp` `App.Task` — app tasks are torn down on every app switch (`tmos_apps.AppManager.set_current_app`), which would leave the WDT unfed on the Settings page. Gated by `config.WATCHDOG_ENABLED` (set `False` when working over USB — an armed WDT can't be stopped without a hardware reset and trips during a slow `mpremote cp` / REPL pause).
  - **Plain-tile dirty tracking**: `DashboardPage._draw()` (`page.py`) does not unconditionally redraw every plain tile (`ValueTile`, `DateTimeTile`, `WeatherTile`) on every tick — each tracks its own `is_dirty()`/`mark_clean()`/`mark_dirty()` state (`tiles.py`), and `_draw()` skips a tile that hasn't changed. This is what makes `WeatherTile`'s vector icon viable despite `DashboardPage`'s 10Hz `execution_frequency`: redraws only happen when the condition/temperature actually changes, not 10x/second. `Page.will_show()` forces a full clear + marks every plain tile dirty again, since switching back to a page via the systray tabs doesn't re-run `setup()` and the screen may have been overwritten by whatever page was shown in between. This dirty-tracking does **not** apply to `Control`-based tiles (`ToggleTile`, `SceneButtonTile`, `DimmableLightTile`) — those are drawn unconditionally by TmOS's own vendored `Page._tick()` loop over `self._controls`, which isn't hand-edited per the vendoring rule above.
- `config.py` — `DEVICE_ID` (needed locally, before any MQTT topic name can be built) plus `DEFAULT_SCREENS`, a minimal fallback shown until the device's real config arrives over MQTT, plus `WATCHDOG_ENABLED`/`WATCHDOG_TIMEOUT_MS` (purely-local runtime flags not worth `dashboard/settings.py`'s validation/UI plumbing — see `watchdog.py` above). It is **not** the tile/entity registry anymore — see README.md's "Declare your tiles" section for the MQTT config-topic contract that replaced it. Tiles still address `dashboard.grid`'s 16-column coordinate system (a "standard" tile is `colspan=4, rowspan=4`).
- This app always boots with `full_res=True` (`OS(layers=1, full_res=True)`) — every `dashboard.grid` constant is tuned for a 480px-wide display; the TmOS default (`full_res=False`, 240x240) would make `GAP=8` dominate a ~7.5px base cell.
